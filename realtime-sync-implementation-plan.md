### 🚀 Real-time Sync (WebSocket): Концепт и План Внедрения [Backend]

#### Цель
Создать на сервере Fastify надежную инфраструктуру на базе WebSocket для мгновенной отправки уведомлений об изменениях данных всем активным клиентам (вкладкам, устройствам) конкретного пользователя. Это обеспечит межустройственную синхронизацию в реальном времени.

#### Концепция и Архитектура
Система будет построена на трех китах, обеспечивающих разделение ответственности и масштабируемость:

1.  **Менеджер Соединений (`wsClients`)**
    *   Централизованное хранилище активных WebSocket-соединений.
    *   Реализован как `Map`, где ключ — `userId`, а значение — `Set` уникальных сокетов этого пользователя.
    *   Позволяет эффективно находить все сессии одного пользователя и рассылать им сообщения.

2.  **Протокол Авторизации через Первое Сообщение**
    *   Поскольку браузерный WebSocket API не позволяет отправлять HTTP-заголовки (например, `Authorization: Bearer ...`), авторизация будет происходить сразу после установки соединения.
    *   **Сценарий:**
        1.  Клиент подключается к WS-эндпоинту.
        2.  Сервер принимает соединение, но ожидает авторизации (устанавливает таймаут ~5 сек).
        3.  Клиент немедленно отправляет первое сообщение: `{ "type": "auth", "token": "..." }`.
        4.  Сервер валидирует токен. В случае успеха — связывает сокет с `userId` и сохраняет в `wsClients`. В случае провала — разрывает соединение.

3.  **Механизм Рассылки (`broadcast`)**
    *   Функция-декоратор `server.broadcast(userId, payload)`, доступная из любого места в приложении Fastify.
    *   Принимает `userId` и объект `payload` (например, `{ type: 'DIARY_ENTRY_UPDATED', ... }`).
    *   Находит все сокеты пользователя в `wsClients` и отправляет им `payload`.

**Принцип работы:**
HTTP-запрос на изменение данных (POST/PUT/DELETE) -> Запись в БД -> Вызов `server.broadcast` -> Рассылка сообщения через WebSocket -> Клиенты получают уведомление.

#### План Внедрения

### ЭТАП 1: Создание базовой инфраструктуры WebSocket

#### Шаг 1.1: Настройка механизма рассылки (broadcast)
- В файле `server.js` создать и зарегистрировать декоратор `broadcast`. Он будет инкапсулировать логику поиска и отправки сообщений клиентам из `wsClients`.

#### Шаг 1.2: Реализация протокола авторизации
- Полностью переписать `api/ws/ws-routes.js`, реализовав логику ожидания `auth` сообщения, таймаут на авторизацию и обработку ошибок.
- Переписать `api/ws/ws-service.js`, вынеся в него функции `authenticateAndAddSocket` и `removeSocket` для инкапсуляции работы с `wsClients`.

### ЭТАП 2: Интеграция с бизнес-логикой (на примере модуля еды)

#### Шаг 2.1: Добавление триггеров в `food-controller.js`
- В методе `createDiaryEntry`, после успешного создания записи в БД, добавить вызов `request.server.broadcast(userId, { type: 'DIARY_ENTRY_CREATED', payload: { dateISO } })`.
- В методе `editDiaryEntry`, после успешного обновления, добавить вызов `request.server.broadcast(userId, { type: 'DIARY_ENTRY_UPDATED', payload: { id: diaryEntry.id, dateISO: diaryEntry.dateISO } })`.
- В методе `deleteDiaryEntry`, **перед** удалением получить данные записи, а **после** успешного удаления вызвать `request.server.broadcast(userId, { type: 'DIARY_ENTRY_DELETED', payload: { id: diaryId, dateISO: entryToDelete.dateISO } })`.

*Примечание:* Мы намеренно отправляем минимальный `payload` (какой день и какая запись затронуты). Это служит "сигналом инвалидации кэша" для клиента, который в ответ сам запросит свежие данные. Это проще и надежнее, чем пытаться отправить полный объект и сливать состояния.

#### РЕЗУЛЬТАТ
- Сервер принимает и авторизует WebSocket-соединения.
- Соединения корректно ассоциируются с пользователями.
- При изменении данных в дневнике питания сервер отправляет уведомления всем активным сессиям этого пользователя.
- Архитектура готова к добавлению real-time уведомлений для других модулей (финансы, настройки).
