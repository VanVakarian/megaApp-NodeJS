### 🚀 Real-time Sync (WebSocket): Концепт и План Внедрения [Backend]

#### Цель
Создать на сервере Fastify надежную инфраструктуру на базе WebSocket для мгновенной отправки уведомлений об изменениях данных всем активным клиентам (вкладкам, устройствам) конкретного пользователя. Это обеспечит межустройственную синхронизацию в реальном времени.

#### Концепция и Архитектура
Система будет построена на трех китах, обеспечивающих разделение ответственности и масштабируемость:

1.  **Менеджер Соединений (`wsClients`)**
    *   Централизованное хранилище активных WebSocket-соединений.
    *   Реализован как `Map`, где ключ — `userId`, а значение — `Set` уникальных сокетов этого пользователя.
    *   Позволяет эффективно находить все сессии одного пользователя и рассылать им сообщения.

2.  **Протокол Авторизации через preValidation Hook**
    *   Использование встроенного механизма Fastify `preValidation` hook для авторизации WebSocket-соединений на этапе установки соединения.
    *   **Сценарий:**
        1.  Клиент подключается к WS-эндпоинту с токеном в query-параметре (`?token=...`) или заголовке.
        2.  Fastify выполняет `preValidation` hook, который валидирует токен перед установкой WebSocket-соединения.
        3.  При успешной валидации — соединение устанавливается и сокет автоматически связывается с `userId`.
        4.  При неуспешной валидации — соединение отклоняется с HTTP 401 ответом до установки WebSocket.

3.  **Механизм Рассылки (`broadcast`) с Исключением Инициатора**
    *   Функция-декоратор `server.broadcast(userId, payload, excludeClientId)`, доступная из любего места в приложении Fastify.
    *   Принимает `userId`, объект `payload` и опциональный `excludeClientId` для исключения инициатора изменений.
    *   Использует уникальный `clientId` для каждого клиента, передаваемый в заголовке `X-Client-ID` и query-параметре `clientId`.
    *   Находит все сокеты пользователя в `wsClients` и отправляет им `payload`, исключая сокет с указанным `clientId`.

4.  **Архитектурная Организация Кода**
    *   Логика WebSocket вынесена в отдельный модуль `api/ws/ws-setup.js` с чистыми функциями.
    *   Декораторы и хуки остаются в `server.js` в соответствии со стилем проекта.
    *   Конфигурируемый heartbeat интервал через переменную окружения `HEARTBEAT_INTERVAL`.

**Принцип работы:**
HTTP-запрос на изменение данных (POST/PUT/DELETE) -> Получение clientId из заголовков -> Запись в БД -> Вызов `server.broadcast(userId, payload, clientId)` -> Рассылка сообщения через WebSocket всем клиентам кроме инициатора -> Остальные клиенты получают уведомление и обновляют интерфейс.

#### План Внедрения

### ЭТАП 1: Создание базовой инфраструктуры WebSocket

#### ✅ Шаг 1.1: Настройка механизма рассылки (broadcast)
- Создать файл `api/ws/ws-setup.js` с функциями `broadcast` и `getClientId`.
- В файле `server.js` зарегистрировать декораторы с проверкой состояния соединений и обработкой ошибок отправки.
- Добавить поддержку исключения инициатора через параметр `excludeClientId`.

#### ✅ Шаг 1.2: Исправление структуры данных wsClients
- Заменить использование массивов на `Set` для эффективного управления соединениями пользователей.
- Обновить все связанные функции для работы с `Set`.

#### ✅ Шаг 1.3: Реализация авторизации через preValidation hook
- Переписать `api/ws/ws-routes.js`, используя `preValidation` hook для авторизации через query-параметр `token` или заголовок `Authorization`.
- Добавить поддержку передачи `clientId` через query-параметр или заголовок `X-Client-ID`.
- Обновить `api/ws/ws-service.js` для автоматического связывания авторизованных соединений с пользователями и сохранения `clientId`.

#### ✅ Шаг 1.4: Добавление механизмов надежности
- Реализовать heartbeat/ping-pong для проверки активности соединений с конфигурируемым интервалом.
- Добавить graceful shutdown для корректного закрытия всех соединений при остановке сервера.
- Вынести heartbeat интервал в переменную окружения `HEARTBEAT_INTERVAL`.

### ЭТАП 2: Интеграция с бизнес-логикой (на примере модуля еды)

#### ✅ Шаг 2.1: Добавление метода получения данных перед удалением
- В `db/db-food.js` добавить метод `getDiaryEntryById` для получения данных записи перед её удалением.
- *Примечание:* В финальной версии убрана проверка существования записи в пользу идемпотентности операции удаления.

#### ✅ Шаг 2.2: Добавление триггеров в `food-controller.js`
- В методе `createDiaryEntry`: добавить broadcast с типом `DIARY_ENTRY_CREATED` и payload `{ id, dateISO }`.
- В методе `editDiaryEntry`: добавить broadcast с типом `DIARY_ENTRY_UPDATED` и payload `{ id, dateISO }`.
- В методе `deleteDiaryEntry`: добавить broadcast с типом `DIARY_ENTRY_DELETED` и payload `{ id }`.
- В методе `processWeight`: добавить broadcast с типом `BODY_WEIGHT_CREATED/UPDATED` и payload `{ dateISO, weight }`.
- Все broadcast'ы получают `clientId` из заголовков и исключают инициатора из рассылки.

*Примечание по payload:* Мы отправляем минимальные, но достаточные данные. Для `create` и `update` операций — `{ id, dateISO }`, чтобы клиент знал какую запись и в каком дне обновить. Для `delete` операций — только `{ id }`, так как клиент сам знает откуда удалить запись. Для веса — `{ dateISO, weight }` для прямого обновления значения.

#### 📋 Требования для Frontend
Для полной работы системы frontend должен:
1. Генерировать уникальный `clientId` при старте приложения (например, `crypto.randomUUID()`).
2. Передавать `clientId` во всех HTTP-запросах через заголовок `X-Client-ID`.
3. Передавать `clientId` при подключении к WebSocket: `ws://server/api/ws?clientId=${clientId}&token=${token}`.
4. Обрабатывать входящие WebSocket сообщения и обновлять интерфейс соответственно.
