# Каталог продуктов: Design Doc

**Версия:** 0.4.0

---

## 1. Контекст и Ключевые Решения

### Проблема
Существующие решения для подсчета калорий заставляют пользователя тратить много времени на поиск продуктов в перегруженных базах данных, сравнивать противоречивые значения КБЖУ и делать слишком много выборов (например, между десятью видами одного и того же творога от разных брендов). Это создает высокое трение и утомляет, в результате чего многие бросают ведение дневника.

### Цель и Пользовательский Опыт
Наша цель — создать **максимально простое и быстрое решение** для ведения дневника питания. Пользовательский опыт должен быть почти мгновенным: найти продукт (текстом, голосом или по фото) и ввести его вес. Все остальное система берет на себя.

Для достижения этой цели в основе архитектуры лежат два ключевых решения:

1.  **Радикальная Простота (UX):** Мы сознательно убираем все лишние шаги и выборы. Система сама определяет усредненные КБЖУ для продуктов с помощью LLM, и пользователь не может их редактировать. Это устраняет трение и возможное желание "схитрить", занизив калории. Мы доверяем усредненным данным от LLM больше, чем ручному вводу.

2.  **Максимальная Обобщенность (Данные):** Чтобы избавить пользователя от выбора между `Яблоко Голден` и `Яблоко Гренни Смит`, наш каталог оперирует только **обобщенными, родовыми понятиями** (`Яблоко`, `Шоколадный батончик`). Задача бэкенда — принудительно агрегировать любой пользовательский ввод до этих общих категорий. При этом, чтобы каталог не превращался в свалку ненужных лично пользователю продуктов, каждый продукт "привязывается" к тем пользователям, которые его добавили, и не виден остальным. Это достигается через связующую таблицу `user_foods_visibility`.

Таким образом, мы создаем систему, которая кажется пользователю его личным, минималистичным каталогом, но под капотом имеет единую, дедуплицированную базу обобщенных продуктов.

## 3. Целевое Решение (To-Be)

### 3.1. Фронтенд (Angular)

- **Стек:** Angular 20+, Signals, Standalone Components, TailwindCSS.
- **Архитектура страницы:** Единая страница добавления в дневник, состоящая из двух взаимоисключающих блоков:
  1.  **Блок Действий (Action Block):** Содержит поле семантического поиска, кнопки для добавления по фото и голосу. Здесь же появляется кнопка "Добавить новый продукт", если поиск не дал результатов.
  2.  **Блок Ввода Граммов (Gram Entry Block):** Появляется после выбора продукта. Содержит простую форму для ввода веса и кнопку "Добавить в дневник".
- **Поведение UI:**
  - Дебаунс поискового ввода (250-300 мс).
  - Плавные переходы между "Блоком Действий" и "Блоком Ввода Граммов".

### 3.2. Бэкенд / API

- **Ключевой принцип:** **Максимальная Обобщенность**. Все эндпоинты, работающие с продуктами, должны нацеливаться на их агрегацию до родовых понятий.
- **Эндпоинты:**
  - `GET /api/foods?query=...` — семантический поиск **обобщенных** продуктов. Запрос "яблоко голден" должен вернуть "Яблоко".
  - `POST /api/foods` — создание нового **обобщенного** продукта на основе детального описания от пользователя.
  - `POST /api/diary/add-by-image` и `POST /api/diary/add-by-voice` — мультимодальный поиск, который внутри себя также выполняет агрегацию до родового понятия.

### 3.3. Модель данных (SQL‑набросок)

Модель решает задачу связи "многие-ко-многим": один обобщенный продукт (в `foods`) может быть виден многим пользователям (связи в `user_foods_visibility`).

```sql
-- Используется SQLite с расширением sqlite-vss для векторного поиска.

-- 1. Таблица УНИКАЛЬНЫХ, ОБОБЩЕННЫХ продуктов
CREATE TABLE IF NOT EXISTS foods (
  id INTEGER PRIMARY KEY,
  -- Название хранит ОБЩЕЕ, агрегированное имя, например, "Яблоко", "Шоколадный батончик".
  name TEXT NOT NULL UNIQUE,

  -- ... (остальные поля КБЖУ)
  is_deleted INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,

  -- === Поля для семантического поиска ===
  description_for_embedding TEXT,
  embedding BLOB
);

-- 2. СВЯЗУЮЩАЯ ТАБЛИЦА для управления видимостью
-- Определяет, какой пользователь "видит" какой продукт в своем поиске.
CREATE TABLE IF NOT EXISTS user_foods_visibility (
  user_id INTEGER NOT NULL,
  food_id INTEGER NOT NULL,
  -- Составной первичный ключ гарантирует уникальность связи
  PRIMARY KEY (user_id, food_id),
  FOREIGN KEY (user_id) REFERENCES users(id),
  FOREIGN KEY (food_id) REFERENCES foods(id)
);

-- 3. Виртуальная таблица VSS для индексации векторов
CREATE VIRTUAL TABLE IF NOT EXISTS vss_foods USING vss0(embedding(768));

-- Индексы для ускорения поиска
CREATE INDEX IF NOT EXISTS idx_foods_name ON foods(name);
CREATE INDEX IF NOT EXISTS idx_visibility_user ON user_foods_visibility(user_id);
```

### 3.4. Архитектура Данных и Пайплайны

#### 3.4.1. Принцип №1: Радикальная Простота (UX)
Система полностью берет на себя ответственность за КБЖУ. Пользователь не может и не должен редактировать эти значения. Это устраняет трение и возможное "читерство". Мы доверяем, что усредненные данные от LLM (возможно, от нескольких для надежности) являются достаточно точными для нашей цели.

#### 3.4.2. Принцип №2: Максимальная Обобщенность (Данные)

- **Пайплайн обогащения (при создании продукта):**
    1.  Пользователь отправляет подробное описание ("домашний борщ на говяжьем бульоне со сметаной").
    2.  Бэкенд отправляет запрос к LLM для генерации **обобщенного названия** ("Борщ") и расчета КБЖУ.
    3.  Система ищет в таблице `foods` продукт с именем "Борщ".
        - **Если найден**, используется его `id`.
        - **Если не найден**, создается новая запись в `foods` и используется ее новый `id`.
    4.  **Создается запись в `user_foods_visibility`**, связывающая `user_id` текущего пользователя и `food_id` (найденный или только что созданный).

- **Логика поиска:**
    1.  Пользовательский запрос преобразуется в вектор.
    2.  `sqlite-vss` находит семантически близкие продукты в **общей** таблице `foods`.
    3.  **Финальный результат фильтруется:** пользователю показываются только те найденные продукты, для которых существует связь с его `user_id` в таблице `user_foods_visibility`.

### 3.5. UX‑потоки

- **Успешный поиск:** Ввод текста/фото/голос → Бэкенд находит "Яблоко" → Открывается "Блок Ввода Граммов" для "Яблока".
- **Неуспешный поиск:** Ввод "экзотический фрукт дуриан" → Бэкенд не находит аналогов → На UI появляется кнопка "Продукт не найден. Добавить в каталог?"
- **Добавление нового продукта:** Нажатие на кнопку → Открывается форма детального описания → Пользователь пишет "дуриан, желтый, с шипами, резкий запах" → Отправка → Бэкенд создает обобщенный продукт "Дуриан" с рассчитанными КБЖУ → Пользователю открывается "Блок Ввода Граммов" для "Дуриана".

### 3.6. Мультимодальный ввод (Фото и Голос)

- **Пайплайн (единый для фото и голоса):**
    1.  **Фронтенд:** Пользователь делает фото или записывает аудио. Данные уходят на соответствующий эндпоинт.
    2.  **Бэкенд:**
        *   Получает данные (картинку или текст после Speech-to-Text).
        *   Отправляет в LLM с **ключевым промптом**: *"Проанализируй эти данные. Верни JSON с **максимально обобщенным, родовым названием** продукта. Например, для 'Яблоко Голден' верни 'Яблоко'. Пример: `{"product": "Куриная грудка"}`"*.
        *   Получает JSON-ответ от LLM.
        *   Использует полученное обобщенное название для **семантического поиска** в каталоге.
        *   Дальнейший флоу зависит от результатов поиска (см. 3.5. UX-потоки).
