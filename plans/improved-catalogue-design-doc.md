# Каталог продуктов: Design Doc

**Версия:** 0.6.0

---

## 1. Контекст и Ключевые Решения

### Проблема
Существующие решения для подсчета калорий заставляют пользователя тратить много времени на поиск продуктов в перегруженных базах данных, сравнивать противоречивые значения КБЖУ и делать слишком много выборов (например, между десятью видами одного и того же творога от разных брендов). Это создает высокое трение и утомляет, в результате чего многие бросают ведение дневника.

### Цель и Пользовательский Опыт
Наша цель — создать **максимально простое и быстрое решение** для ведения дневника питания. Пользовательский опыт должен быть почти мгновенным: найти продукт (текстом, голосом или по фото) и ввести его вес. Все остальное система берет на себя.

Для достижения этой цели в основе архитектуры лежат два ключевых решения:

1.  **Радикальная Простота (UX):** Мы сознательно убираем все лишние шаги и выборы. Система сама определяет усредненные КБЖУ для продуктов с помощью LLM, и пользователь не может их редактировать. Это устраняет трение и возможное желание "схитрить", занизив калории. Мы доверяем усредненным данным от LLM больше, чем ручному вводу.

2.  **Максимальная Обобщенность (Данные):** Чтобы избавить пользователя от выбора между `Яблоко Голден` и `Яблоко Гренни Смит`, наш каталог оперирует только **обобщенными, родовыми понятиями** (`Яблоко`, `Шоколадный батончик`). Задача бэкенда — принудительно агрегировать любой пользовательский ввод до этих общих категорий.

Поскольку приложение предназначено для ограниченного числа пользователей и не планируется расширение пользовательской базы, мы используем **единый общий каталог** для всех пользователей. Семантический поиск обеспечивает показ только релевантных результатов, что исключает проблему засорения каталога. Любой пользователь может добавить продукт, который будет доступен всем, но найти его можно только при целенаправленном поиске.

Таким образом, мы создаем систему с единой, дедуплицированной базой обобщенных продуктов, доступной всем пользователям.

## 2. Текущее Состояние (As-Is)

### 2.1. Архитектура базы данных
- **SQLite** с простыми таблицами без сложных связей
- Каталог продуктов в таблице `foodCatalogue` (id, name, kcals)
- Дневник питания в таблице `foodDiary` со ссылкой на `foodCatalogueId`

### 2.2. API структура (Fastify)
- **Принятые паттерны**: Controller → Service → DB layers
- **Стандартные ответы**: `{ result: boolean, data?: any, error?: string }`
- **Middleware**: authMiddleware для всех защищенных эндпоинтов
- **WebSocket**: Real-time синхронизация через broadcast system
- **Миграции**: Структурированная система с бэкапами

### 2.3. Текущие эндпоинты
- `GET /api/food/catalogue` - получение всего каталога
- `POST /api/food/catalogue` - создание нового продукта

### 2.4. Проблемы текущей архитектуры
- Отсутствие семантического поиска
- Нет дедупликации - каждый пользователь может создавать дубли
- Простые названия без обобщения
- Нет интеграции с LLM для автоматического определения КБЖУ
- Нет мультимодального ввода (фото/голос)

## 3. Целевое Решение (To-Be)

### 3.1. Фронтенд (Angular)

- **Стек:** Angular 20+, Signals, Standalone Components, TailwindCSS.
- **Архитектура страницы:** Единая страница добавления в дневник, состоящая из двух взаимоисключающих блоков:
  1.  **Блок Действий (Action Block):** Содержит поле семантического поиска, кнопки для добавления по фото и голосу. Здесь же появляется кнопка "Добавить новый продукт", если поиск не дал результатов.
  2.  **Блок Ввода Граммов (Gram Entry Block):** Появляется после выбора продукта. Содержит простую форму для ввода веса и кнопку "Добавить в дневник".
- **Поведение UI:**
  - Дебаунс поискового ввода (250-300 мс).
  - Плавные переходы между "Блоком Действий" и "Блоком Ввода Граммов".
- **Кэширование поиска:**
  - localStorage: ключ = строка запроса, значение = массив ID (макс. 20).
  - При вводе проверка кэша → мгновенный ответ или запрос на сервер с сохранением результата.
  - Debounced запись в localStorage.

### 3.2. Бэкенд / API

#### 3.2.1. Архитектурные принципы
- **Следуем принятой структуре**: Controller → Service → DB layers
- **Стандартизированные ответы**: `{ result: boolean, data?: any, error?: string }`
- **Middleware**: `authController.authMiddleware` для всех защищенных эндпоинтов
- **Real-time обновления**: WebSocket broadcast для синхронизации между клиентами
- **Миграционная система**: Используем существующую систему миграций с бэкапами

#### 3.2.2. Ключевой принцип: Максимальная Обобщенность
Все эндпоинты, работающие с продуктами, должны нацеливаться на их агрегацию до родовых понятий.

#### 3.2.3. Новые эндпоинты

**GET /api/food/search** - семантический поиск обобщенных продуктов
- Параметры: query (текст запроса), limit (количество результатов)
- Возвращает записи каталога, доступные всем пользователям
- Ответ: массив найденных записей каталога с коэффициентами релевантности

**POST /api/food/create-generalized** - создание обобщенного продукта через LLM
- Тело запроса: описание продукта в свободной форме
- Ответ: созданная запись каталога и флаг новизны

**POST /api/food/analyze-image** - анализ фото продукта
- Тело запроса: FormData с файлом изображения
- Ответ: предположение о записи каталога или null

#### 3.2.4. Модифицированные эндпоинты

**GET /api/food/catalogue** - получение полного каталога
- Возвращает все записи каталога, доступные всем пользователям
- Ответ: полный список продуктов с расширенными данными КБЖУ

### 3.3. Модель данных и миграция

#### 3.3.1. Новая схема базы данных

**Расширение таблицы `foodCatalogue`:**
Добавить новые поля для расширенных КБЖУ данных и семантического поиска:
- `protein` (REAL) - содержание белков
- `fat` (REAL) - содержание жиров
- `carbs` (REAL) - содержание углеводов
- `fiber` (REAL) - содержание клетчатки
- `descriptionForEmbedding` (TEXT) - описание для векторизации
- `embedding` (BLOB) - векторное представление для поиска

Добавить уникальное ограничение на поле `name`.

**Векторное хранение:**
Векторные представления будут храниться в поле `embedding` (BLOB) основной таблицы `foodCatalogue`. Поиск по векторам будет производиться на уровне JavaScript с использованием косинусного расстояния.

#### 3.3.2. Миграция данных

**Удаление устаревшей персонализации:**
Удалить поле `selectedCatalogueIds` из таблицы `foodSettings`, так как каталог становится единым для всех пользователей.

### 3.4. Архитектура сервисов и интеграций

#### 3.4.1. Service Layer структура
Следуя принятой в проекте архитектуре:

**food-service.js** - содержит бизнес-логику для работы с продуктами:
- Семантический поиск записей каталога для всех пользователей
- Создание обобщенных записей каталога через LLM
- Управление единым каталогом продуктов

**food-controller.js** - HTTP обработчики для API эндпоинтов:
- Стандартизированные ответы `{ result, data, error }`
- Валидация входящих данных
- WebSocket уведомления при изменениях

**db-food.js** - операции с базой данных:
- Векторный поиск на JavaScript-уровне с косинусным расстоянием
- CRUD операции для записей каталога
- Сериализация/десериализация векторных представлений в BLOB

#### 3.4.2. LLM интеграция

**llm-service.js** - новый сервис для работы с языковыми моделями:
- Генерация обобщенных названий продуктов на основе пользовательского описания
- Анализ изображений продуктов для извлечения названия и КБЖУ
- Обработка голосовых транскриптов для определения продуктов

**Структура ответа от LLM:**
- Обобщенное название продукта (например, "Яблоко" вместо "Яблоко Голден")
- Полные данные КБЖУ: калории, белки, жиры, углеводы, клетчатка
- Коэффициент уверенности для валидации результата

#### 3.4.3. WebSocket интеграция
Используем существующую broadcast систему для уведомлений о изменениях в каталоге продуктов. При добавлении новых записей каталога отправляются real-time уведомления всем подключенным клиентам для синхронизации интерфейса.

#### 3.4.4. Миграционная стратегия
Используем существующую систему миграций с созданием файла миграции `002-to-003.js`, который содержит все необходимые изменения схемы базы данных. Миграция запускается через стандартную команду проекта.

#### 3.4.5. Упрощенная архитектура векторного поиска

**Принципы хранения векторов:**
- Векторные представления сохраняются в поле `embedding` (BLOB) основной таблицы `foodCatalogue`
- Сериализация Float32Array в Buffer для хранения в SQLite
- Десериализация Buffer обратно в Float32Array для вычислений

**Алгоритм поиска на JavaScript-уровне:**
- Загрузка всех записей каталога с векторными представлениями
- Вычисление косинусного расстояния между поисковым запросом и каждой записью
- Сортировка результатов по релевантности (минимальное расстояние = максимальная релевантность)
- Ограничение количества возвращаемых результатов

**Преимущества упрощенного подхода:**
- Отсутствие внешних зависимостей от sqlite-vec
- Простота развертывания и отладки
- Оптимальная производительность для каталогов до 1,000 записей
- Полный контроль над алгоритмом поиска и возможность его оптимизации

### 3.5. UX‑потоки

- **Успешный поиск:** Ввод текста/фото/голос → Бэкенд находит "Яблоко" → Открывается "Блок Ввода Граммов" для "Яблока".
- **Неуспешный поиск:** Ввод "экзотический фрукт дуриан" → Бэкенд не находит аналогов → На UI появляется кнопка "Продукт не найден. Добавить в каталог?"
- **Добавление нового продукта:** Нажатие на кнопку → Открывается форма детального описания → Пользователь пишет "дуриан, желтый, с шипами, резкий запах" → Отправка → Бэкенд создает обобщенный продукт "Дуриан" с рассчитанными КБЖУ → Пользователю открывается "Блок Ввода Граммов" для "Дуриана".

### 3.6. Мультимодальный ввод (Фото и Голос)

#### 3.6.1. Архитектура по типам медиа

**Фото (HTTP REST API):**
1.  **Фронтенд:** Пользователь делает фото → отправка через `POST /api/food/analyze-image`
2.  **Бэкенд:** Получает изображение → анализ через LLM Vision → семантический поиск → ответ с найденными продуктами

**Аудио (Realtime WebSocket Streaming):**
1.  **Фронтенд:** Пользователь нажимает кнопку записи → MediaRecorder начинает захват аудио чанками (100ms)
2.  **WebSocket соединение:** Аудио чанки передаются через WebSocket в real-time
3.  **Бэкенд:** Проксирует аудио на OpenAI Realtime API (`wss://api.openai.com/v1/realtime?intent=transcription`)
4.  **Streaming транскрипция:** OpenAI возвращает промежуточные результаты распознавания речи
5.  **Семантический поиск:** По каждому обновлению транскрипта выполняется поиск (с дебаунсом)
6.  **Real-time результаты:** Найденные продукты отправляются обратно через WebSocket

#### 3.6.2. UX флоу для аудио стриминга

1.  **Инициация записи:** Пользователь нажимает кнопку → WebSocket соединение устанавливается
2.  **Процесс записи:** Аудио чанки отправляются → транскрипт обновляется в реальном времени → результаты поиска показываются
3.  **Завершение:** Пользователь отпускает кнопку → финальный результат → переход к выбору продукта

#### 3.6.3. Error handling
Следуя принятому в проекте паттерну обработки ошибок:
- **HTTP (фото)**: Стандартные коды ошибок и `{ result: false, error: string }`
- **WebSocket (аудио)**: Graceful degradation при обрыве соединения, reconnection логика
- **Fallback**: При недоступности Realtime API переход на обычный STT + HTTP


## 4. Нефункциональные Требования

### 4.1. Производительность
- **Поисковые запросы**: < 200ms для семантического поиска (JS-уровень для до 1000 записей)
- **LLM интеграция**: < 3s для генерации обобщенного продукта
- **WebSocket уведомления**: < 50ms для broadcast сообщений
- **Поддержка векторного поиска**: до 1,000 продуктов с отличной производительностью на JS-уровне

### 4.2. Надежность
- **Fallback стратегия**: при недоступности LLM - простой текстовый поиск
- **Миграция данных**: с полным бэкапом перед изменениями
- **Graceful degradation**: работа без векторного поиска при проблемах с embeddings

### 4.3. Безопасность
- **Аутентификация**: все эндпоинты защищены `authMiddleware`
- **Единый каталог**: все пользователи имеют доступ к общему каталогу
- **Валидация**: схемы Fastify для всех входящих данных

### 4.4. Масштабируемость
- **Горизонтальное масштабирование**: возможность добавления read-replicas для поиска
- **Кэширование**: векторных представлений для часто используемых запросов
- **Batch обработка**: векторизации для множественных продуктов
- **JavaScript поиск**: оптимальная производительность для каталогов до 1,000 записей

## Приложение A: Типы и Примеры

### A.1. Структура данных

**Основной интерфейс продукта (CatalogueEntry):**
- Уникальный идентификатор записи каталога
- Обобщенное название (например, "Яблоко")
- Данные КБЖУ: калории, белки, жиры, углеводы, клетчатка (опционально)
- Описание для векторизации (опционально)

**Результат поиска (CatalogueSearchResult):**
- Объект записи каталога
- Коэффициент релевантности от 0 до 1

**Стандартный ответ API (SearchResponse):**
- Флаг успешности операции
- Данные (массив результатов поиска или null)
- Сообщение об ошибке (при неудаче)

**Запрос на создание продукта:**
- Текстовое описание продукта от пользователя

**Ответ от LLM сервиса:**
- Обобщенное название продукта
- Структура КБЖУ (калории, белки, жиры, углеводы, клетчатка)
- Коэффициент уверенности модели

**WebSocket события:**
- Тип события (добавление в каталог, изменение видимости)
- Полезная нагрузка с данными записи каталога и действием

### A.2. Примеры API запросов/ответов

#### Семантический поиск
```http
GET /api/food/search?query=яблоко гренни смит&limit=5

200 OK
```
Возвращает массив найденных записей каталога с коэффициентами релевантности. Каждый элемент содержит полную информацию о записи каталога (ID, название, КБЖУ) и оценку соответствия поисковому запросу.

#### Создание обобщенного продукта
```http
POST /api/food/create-generalized
Content-Type: application/json

{
  "description": "домашний борщ на говяжьем бульоне со сметаной"
}

201 Created
```
Возвращает созданную запись каталога с автоматически сгенерированными данными КБЖУ и флагом `isNew`, указывающим была ли запись каталога создана заново или найдена в существующем каталоге.

#### Анализ изображения
```http
POST /api/food/analyze-image
Content-Type: multipart/form-data

[binary image data]

200 OK
```
Возвращает предположение о записи каталога на основе анализа изображения, включающее полную информацию о распознанной записи каталога с данными КБЖУ, либо null если запись каталога не удалось определить.

#### Realtime аудио стриминг
```javascript
// WebSocket соединение для аудио
WebSocket: wss://your-domain/api/ws

// Начало записи
{
  "type": "START_VOICE_RECORDING"
}

// Аудио чанки в real-time
{
  "type": "AUDIO_CHUNK",
  "data": "base64_audio_data",
  "sequence": 1
}

// Ответ с промежуточными результатами
{
  "type": "VOICE_SEARCH_RESULTS",
  "transcript": "яблоко зеленое",
  "products": [...],
  "confidence": 0.85
}
```
Возвращает streaming результаты поиска на основе промежуточной транскрипции через OpenAI Realtime API с автоматическим Voice Activity Detection.

### A.3. Основные операции с данными

#### Семантический поиск по общему каталогу
1. Загрузить все записи каталога с векторными представлениями
2. Выполнить векторный поиск на JavaScript-уровне с использованием косинусного расстояния
3. Отсортировать результаты по релевантности и ограничить количество

#### Создание записи каталога с проверкой существования
1. Проверить существование записи каталога с таким же названием
2. Если запись каталога не найдена - создать новую запись в `foodCatalogue` с полными КБЖУ данными
3. Продукт автоматически становится доступным всем пользователям

**Миграционный путь**:
- Текущая архитектура легко расширяется для поддержки персонализации

### 7.3. Социальные функции
**Рекомендации**: Система рекомендаций продуктов на основе предпочтений пользователей

**История популярности**: Отслеживание часто используемых продуктов для приоритизации в поиске

#### Управление векторными представлениями
**Сохранение embedding:**
- Сериализация Float32Array в Buffer для сохранения в BLOB поле
- Обновление записи каталога с новым векторным представлением

**Извлечение embedding:**
- Загрузка BLOB данных из базы
- Десериализация Buffer обратно в Float32Array для вычислений

#### Алгоритм косинусного расстояния
- Вычисление скалярного произведения векторов
- Расчет норм векторов
- Определение косинусного расстояния как меры похожести
