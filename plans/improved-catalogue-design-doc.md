# Каталог продуктов: Design Doc

**Версия:** 0.7.0

---

## 1. Контекст и Ключевые Решения

### Проблема
Существующие решения для подсчета калорий заставляют пользователя тратить много времени на поиск продуктов в перегруженных базах данных, сравнивать противоречивые значения КБЖУ и делать слишком много выборов (например, между десятью видами одного и того же творога от разных брендов). Это создает высокое трение и утомляет, в результате чего многие бросают ведение дневника.

### Цель и Пользовательский Опыт
Наша цель — создать **максимально простое и быстрое решение** для ведения дневника питания. Пользовательский опыт должен быть почти мгновенным: найти продукт (текстом, голосом или по фото) и ввести его вес. Все остальное система берет на себя.

Для достижения этой цели в основе архитектуры лежат два ключевых решения:

1.  **Радикальная Простота (UX):** Мы сознательно убираем все лишние шаги и выборы. Система сама определяет усредненные КБЖУ для продуктов с помощью LLM, и пользователь не может их редактировать. Это устраняет трение и возможное желание "схитрить", занизив калории. Мы доверяем усредненным данным от LLM больше, чем ручному вводу.

2.  **Максимальная Обобщенность (Данные):** Чтобы избавить пользователя от выбора между `Яблоко Голден` и `Яблоко Гренни Смит`, наш каталог оперирует только **обобщенными, родовыми понятиями** (`Яблоко`, `Шоколадный батончик`). Задача бэкенда — принудительно агрегировать любой пользовательский ввод до этих общих категорий.

Поскольку приложение предназначено для ограниченного числа пользователей и не планируется расширение пользовательской базы, мы используем **единый общий каталог** для всех пользователей. Семантический поиск обеспечивает показ только релевантных результатов, что исключает проблему засорения каталога. Любой пользователь может добавить продукт, который будет доступен всем, но найти его можно только при целенаправленном поиске.

Таким образом, мы создаем систему с единой, дедуплицированной базой обобщенных продуктов, доступной всем пользователям.

## 2. Текущее Состояние (As-Is)

### 2.1. Архитектура базы данных
- **SQLite** с простыми таблицами без сложных связей
- Каталог продуктов в таблице `foodCatalogue` (id, name, kcals)
- Дневник питания в таблице `foodDiary` со ссылкой на `foodCatalogueId`

### 2.2. API структура (Fastify)
- **Принятые паттерны**: Controller → Service → DB layers
- **Стандартные ответы**: `{ result: boolean, data?: any, error?: string }`
- **Middleware**: authMiddleware для всех защищенных эндпоинтов
- **WebSocket**: Real-time синхронизация через broadcast system
- **Миграции**: Структурированная система с бэкапами

### 2.3. Текущие эндпоинты
- `GET /api/food/catalogue` - получение всего каталога
- `POST /api/food/catalogue` - создание нового продукта

### 2.4. Проблемы текущей архитектуры
- Отсутствие семантического поиска
- Нет дедупликации - каждый пользователь может создавать дубли
- Простые названия без обобщения
- Нет интеграции с LLM для автоматического определения КБЖУ
- Нет мультимодального ввода (фото/голос)

## 3. Целевое Решение (To-Be)

### 3.1. Фронтенд (Angular)

- **Стек:** Angular 20+, Signals, Standalone Components, TailwindCSS.
- **Миграционная стратегия:** Поэтапное внедрение нового функционала с сохранением старой системы до полной стабилизации.
- **Точка внедрения:** Модернизация существующей модалки добавления в дневнике (food-diary.component.html), затем вынос в отдельные компоненты.

#### 3.1.1. Архитектура новой системы

**Базовая реализация в модалке дневника:**
1.  **Блок Действий (Action Block):** Семантический поиск + кнопки фото/голос + создание через LLM при отсутствии результатов.
2.  **Блок Ввода Граммов (Gram Entry Block):** Форма выбора продукта и ввода веса после поиска.
3.  **Блок Формы Продукта (Product Form Block):** Универсальная форма для создания и редактирования продуктов с режимами `create` и `edit`.
4.  **Взаимоисключающие состояния:** Плавные переходы между блоками в рамках одной модалки.

#### 3.1.2. Техническая реализация

**WebSocket + localStorage кэширование:**
- При вводе запроса → мгновенная проверка localStorage кэша (ключ = запрос, значение = массив ID)
- Параллельно отправка WebSocket запроса на бэкенд **на каждое нажатие клавиши** (без дебаунса)
- Если кэш найден → мгновенное отображение результатов
- При получении ответа от бэкенда → сверка с кэшем → обновление UI при изменениях → обновление кэша
- Real-time отклик без задержек для максимально быстрого UX

**Legacy поиск как fallback:**
- Переключатель в поле поиска (префикс-иконка) для активации Legacy режима
- Legacy поиск по текстовому совпадению в поле `legacyName` записей каталога
- Два независимых сигнала результатов: семантический и Legacy (не скрещиваются)
- Одинаковый дизайн карточек для обоих типов поиска
- Уведомление пользователю о режиме Legacy поиска
- Легкое удаление Legacy функционала после стабилизации семантического поиска

**Поэтапная миграция компонентов:**
- **Этап 1:** Функционал в модалке дневника (минимальные изменения)
- **Этап 2:** Постепенное комментирование старой системы каталога
- **Этап 3:** Вынос логики в отдельные компоненты после стабилизации
- **Этап 4:** Полное удаление устаревших компонентов и данных

### 3.2. Бэкенд / API

#### 3.2.1. Архитектурные принципы
- **Следуем принятой структуре**: Controller → Service → DB layers
- **Стандартизированные ответы**: `{ result: boolean, data?: any, error?: string }`
- **Middleware**: `authController.authMiddleware` для всех защищенных эндпоинтов
- **Real-time обновления**: WebSocket broadcast для синхронизации между клиентами
- **Миграционная система**: Используем существующую систему миграций с бэкапами

#### 3.2.2. Ключевой принцип: Максимальная Обобщенность
Все эндпоинты, работающие с продуктами, должны нацеливаться на их агрегацию до родовых понятий.

#### 3.2.3. Новые эндпоинты

**GET /api/food/search** - семантический поиск обобщенных продуктов
- Параметры: query (текст запроса), limit (количество результатов)
- Возвращает записи каталога, доступные всем пользователям
- Ответ: массив найденных записей каталога с коэффициентами релевантности

**POST /api/food/generate-product-preview** - генерация данных продукта без создания в БД
- Тело запроса: описание продукта в свободной форме (строка)
- Назначение: первый этап добавления продукта - получение сгенерированных данных для проверки
- LLM генерирует обобщенное название и полные КБЖУ данные
- Данные НЕ сохраняются в базу, только возвращаются пользователю для проверки
- Ответ: сгенерированные данные (название, КБЖУ, описание, уровень уверенности)

**POST /api/food/save-product** - универсальное сохранение продукта (создание или обновление)
- Тело запроса: `{ id?: number, name, kcals, protein, fat, carbs, fiber, description }`
- Назначение: универсальный эндпоинт для создания новых и редактирования существующих продуктов
- **Логика создания (если `id` не передан)**:
  - Проверяет существование продукта с таким именем
  - Если продукт существует: возвращает ошибку `400: "Product with this name already exists"`
  - Если продукт не существует: создает новую запись с полными данными и генерирует embedding
  - WebSocket broadcast: `CATALOGUE_ENTRY_SAVED` с полной записью каталога
- **Логика обновления (если `id` передан)**:
  - Проверяет существование записи с указанным ID
  - Если запись не найдена: возвращает ошибку `404: "Product not found"`
  - Проверяет конфликт имен с другими записями: `WHERE name = :name AND id != :id`
  - Если конфликт имен: возвращает ошибку `400: "Product with this name already exists"`
  - Сравнивает старые и новые значения `name` и `description`
  - При изменении `name` или `description`: пересчитывает embedding через LLM (экономия API вызовов)
  - При отсутствии изменений: не трогает embedding, обновляет только измененные поля КБЖУ
  - Обновляет все поля записи
  - WebSocket broadcast: `CATALOGUE_ENTRY_SAVED` с обновленной записью каталога
- Все поля обязательны и могут быть отредактированы пользователем
- Валидация: kcals (0-1000), protein/fat/carbs (0-100), fiber (0-50), name (1-100 символов), description (1-2000 символов)
- Race conditions: "last write wins" - приемлемо для малого числа пользователей, версионирование не требуется
- Ответ: созданная или обновленная запись каталога

**POST /api/food/analyze-image** - анализ фото продукта
- Тело запроса: FormData с файлом изображения
- Ответ: предположение о записи каталога или null

**POST /api/food/merge-duplicates** - объединение дублирующих продуктов
- Тело запроса: массив ID записей каталога для объединения
- Ответ: ID основной записи и количество обновленных записей дневника

#### 3.2.4. Модифицированные эндпоинты

**GET /api/food/catalogue** - получение полного каталога
- Возвращает все записи каталога, доступные всем пользователям
- Ответ: полный список продуктов с расширенными данными КБЖУ

### 3.3. Модель данных и миграция

#### 3.3.1. Новая схема базы данных

**Расширение таблицы `foodCatalogue`:**
Добавить новые поля для расширенных КБЖУ данных и семантического поиска:
- `protein` (REAL) - содержание белков
- `fat` (REAL) - содержание жиров
- `carbs` (REAL) - содержание углеводов
- `fiber` (REAL) - содержание клетчатки
- `descriptionForEmbedding` (TEXT) - описание для векторизации
- `embedding` (BLOB) - векторное представление для поиска
- `legacyName` (TEXT) - исходное название для Legacy текстового поиска

Добавить уникальное ограничение на поле `name`.

**Векторное хранение:**
Векторные представления будут храниться в поле `embedding` (BLOB) основной таблицы `foodCatalogue`. Поиск по векторам будет производиться на уровне JavaScript с использованием косинусного расстояния.

#### 3.3.2. Миграция данных

**Удаление устаревшей персонализации:**
Удалить поле `selectedCatalogueIds` из таблицы `foodSettings`, так как каталог становится единым для всех пользователей.

### 3.4. Архитектура сервисов и интеграций

#### 3.4.1. Service Layer структура
Следуя принятой в проекте архитектуре:

**food-service.js** - содержит бизнес-логику для работы с продуктами:
- Семантический поиск записей каталога для всех пользователей
- Создание обобщенных записей каталога через LLM
- Управление единым каталогом продуктов

**food-controller.js** - HTTP обработчики для API эндпоинтов:
- Стандартизированные ответы `{ result, data, error }`
- Валидация входящих данных
- WebSocket уведомления при изменениях

**db-food.js** - операции с базой данных:
- Векторный поиск на JavaScript-уровне с косинусным расстоянием
- CRUD операции для записей каталога
- Сериализация/десериализация векторных представлений в BLOB

#### 3.4.2. LLM интеграция

**llm-service.js** - новый сервис для работы с языковыми моделями:
- Генерация обобщенных названий продуктов на основе пользовательского описания
- Анализ изображений продуктов для извлечения названия и КБЖУ
- Обработка голосовых транскриптов для определения продуктов

**Production-ready генерация (`ai-service.generateGeneralizedProduct`):**
- **Sequential fallback**: модели вызываются последовательно (не параллельно)
- **Три продовые модели** из `AI_FOOD_TEST_MODELS`:
  1. `qwen/qwen3-coder` - первая попытка
  2. `deepseek/deepseek-chat-v3.1` - fallback #1
  3. `meta-llama/llama-3.1-405b-instruct` - fallback #2
- **ULTIMATE-1 промпт** из `AI_FOOD_GENERATION_PROMPTS`:
  - Каноническое название (2-4 слова, без брендов)
  - Поисково-оптимизированное описание с тегами
  - **Полные КБЖУ данные на 100г продукта** (kcals, protein, fat, carbs, fiber)
  - Реалистичные усреднённые значения для каждого типа продукта
  - Строгая идентификация без выдуманных фактов
- **Расширенная JSON схема** в системном промпте:
  ```json
  {
    "name": "название",
    "description": "описание с тегами",
    "kcals": число (0-1000),
    "protein": число (0-100),
    "fat": число (0-100),
    "carbs": число (0-100),
    "fiber": число (0-50)
  }
  ```
- **Robust JSON parsing** с 5 стратегиями (`parseJSONWithMultipleStrategies`):
  1. Clean JSON - прямой parse
  2. Remove markdown blocks - удаление ```json блоков
  3. Extract JSON with regex - поиск регулярками
  4. Extract between braces - извлечение между { и }
  5. Line-by-line reconstruction - построчная реконструкция
  - Валидация наличия name, description и всех КБЖУ полей (kcals, protein, fat, carbs, fiber)
- **Прямой вызов OpenRouter API** (`callOpenRouterDirectly`) для максимального контроля
- **Остановка при первом успехе**: экономия токенов и времени

**Структура ответа от LLM:**
- Обобщенное название продукта (например, "Яблоко" вместо "Яблоко Golden")
- Полные данные КБЖУ: калории, белки, жиры, углеводы, клетчатка
- Коэффициент уверенности для валидации результата
- Описание для векторного поиска

#### 3.4.3. WebSocket интеграция
Используем существующую broadcast систему для уведомлений о изменениях в каталоге продуктов. При добавлении и обновлении записей каталога отправляются real-time уведомления всем подключенным клиентам для синхронизации интерфейса.

**WebSocket события для каталога:**
- `CATALOGUE_ENTRY_SAVED` - универсальное событие при создании или обновлении продукта через `/save-product`
- Payload содержит полную запись каталога (id, name, kcals, protein, fat, carbs, fiber, description, legacyName, embedding) для синхронизации localStorage на всех клиентах
- Клиент определяет создание/обновление по наличию записи с данным ID в локальном каталоге

#### 3.4.4. Миграционная стратегия
Используем существующую систему миграций с созданием файла миграции `002-to-003.js`, который содержит все необходимые изменения схемы базы данных. Миграция запускается через стандартную команду проекта.

#### 3.4.5. Упрощенная архитектура векторного поиска

**Принципы хранения векторов:**
- Векторные представления сохраняются в поле `embedding` (BLOB) основной таблицы `foodCatalogue`
- Сериализация Float32Array в Buffer для хранения в SQLite
- Десериализация Buffer обратно в Float32Array для вычислений

**Алгоритм поиска на JavaScript-уровне:**
- Загрузка всех записей каталога с векторными представлениями
- Вычисление косинусного расстояния между поисковым запросом и каждой записью
- Сортировка результатов по релевантности (минимальное расстояние = максимальная релевантность)
- Ограничение количества возвращаемых результатов

**Преимущества упрощенного подхода:**
- Отсутствие внешних зависимостей от sqlite-vec
- Простота развертывания и отладки
- Оптимальная производительность для каталогов до 1,000 записей
- Полный контроль над алгоритмом поиска и возможность его оптимизации

### 3.5. UX‑потоки

- **Успешный поиск:** Ввод текста/фото/голос → Бэкенд находит "Яблоко" → Открывается "Блок Ввода Граммов" для "Яблока".
- **Неуспешный поиск:** Ввод "экзотический фрукт дуриан" → Бэкенд не находит аналогов → На UI появляется кнопка "Добавить как новую еду".
- **Редактирование продукта:**
  - Пользователь ищет продукт → выбирает из результатов → открывается "Блок Ввода Граммов"
  - В блоке ввода граммов появляется кнопка "Редактировать" рядом с названием продукта
  - Нажатие на "Редактировать" → открывается "Блок Формы Продукта" в режиме `edit`
  - Форма предзаполнена текущими данными выбранного продукта (название, КБЖУ, описание)
  - Все поля редактируемые
  - Кнопка "Сохранить изменения"
  - Нажатие "Сохранить" → запрос `POST /save-product` с ID продукта и обновленными данными
  - Бэкенд проверяет существование записи, конфликт имен (с другими записями) и обновляет запись
  - При изменении названия/описания → пересчет embedding
  - При отсутствии изменений названия/описания → обновление только полей КБЖУ без пересчета embedding (экономия API вызовов)
  - WebSocket broadcast: `CATALOGUE_ENTRY_SAVED` → синхронизация локального каталога
  - После успешного обновления → возврат к "Блоку Ввода Граммов" с обновленными данными продукта
- **Добавление нового продукта (двухэтапный процесс):**
  1. **Этап генерации (Preview):**
     - Пользователь вводит описание продукта (например, "виски шотландский односолодовый")
     - Семантический поиск не находит подходящих результатов
     - Появляется кнопка "Добавить как новую еду"
     - Нажатие на кнопку → запрос `POST /generate-product-preview` с текстом из поля поиска
     - Бэкенд генерирует данные через LLM БЕЗ создания в БД
     - Возврат: обобщенное название ("Виски"), КБЖУ, описание для embedding
  2. **Этап проверки и редактирования:**
     - Открывается "Блок Формы Продукта" в режиме `create` с предзаполненными сгенерированными данными
     - Все поля редактируемые: название, калории, белки, жиры, углеводы, клетчатка, описание
     - Пользователь может изменить любые значения при необходимости
     - Кнопка "Подтвердить" / "Добавить"
  3. **Этап подтверждения:**
     - Нажатие "Подтвердить" → запрос `POST /save-product` БЕЗ поля `id` (создание нового)
     - Бэкенд проверяет существование по имени
     - **Если продукт существует:** возврат ошибки `400: "Product with this name already exists"`, показ сообщения пользователю, предложение изменить название
     - **Если продукт не существует:** создает новую запись с полными данными и генерирует embedding
     - WebSocket broadcast: `CATALOGUE_ENTRY_SAVED`
     - Возврат: созданная запись каталога
  4. **После успешного создания:**
     - "Блок Формы Продукта" закрывается
     - Автоматически подставляется изначальный запрос пользователя в поле поиска
     - Запускается семантический поиск
     - Ожидаем увидеть новый продукт в топе результатов
     - Пользователь выбирает продукт → переход к "Блоку Ввода Граммов"
- **Legacy поиск fallback:** Пользователь вводит запрос → семантический поиск не находит ожидаемый продукт → клик на префикс-иконку в поле поиска → переключение на Legacy режим → отображение уведомления "Legacy поиск" → результаты семантического поиска очищаются → запускается текстовый поиск по `legacyName` → отображение Legacy результатов в том же дизайне.
- **Дедупликация продуктов:** Админ-интерфейс с поисковым полем → расширенные карточки с полными данными КБЖУ → выбор дублирующих продуктов галочками → подтверждение объединения → бэкенд определяет основную запись по частоте использования → обновление всех записей дневника → удаление неиспользуемых дубликатов.

### 3.6. Мультимодальный ввод (Фото и Голос)

#### 3.6.1. Архитектура по типам медиа

**Фото (HTTP REST API):**
1.  **Фронтенд:** Пользователь делает фото → отправка через `POST /api/food/analyze-image`
2.  **Бэкенд:** Получает изображение → анализ через LLM Vision → семантический поиск → ответ с найденными продуктами

**Аудио (Realtime WebSocket Streaming):**
1.  **Фронтенд:** Пользователь нажимает кнопку записи → MediaRecorder начинает захват аудио чанками (100ms)
2.  **WebSocket соединение:** Аудио чанки передаются через WebSocket в real-time
3.  **Бэкенд:** Проксирует аудио на OpenAI Realtime API (`wss://api.openai.com/v1/realtime?intent=transcription`)
4.  **Streaming транскрипция:** OpenAI возвращает промежуточные результаты распознавания речи
5.  **Семантический поиск:** По каждому обновлению транскрипта выполняется поиск (с дебаунсом)
6.  **Real-time результаты:** Найденные продукты отправляются обратно через WebSocket

#### 3.6.2. UX флоу для аудио стриминга

1.  **Инициация записи:** Пользователь нажимает кнопку → WebSocket соединение устанавливается
2.  **Процесс записи:** Аудио чанки отправляются → транскрипт обновляется в реальном времени → результаты поиска показываются
3.  **Завершение:** Пользователь отпускает кнопку → финальный результат → переход к выбору продукта

#### 3.6.3. Error handling
Следуя принятому в проекте паттерну обработки ошибок:
- **HTTP (фото)**: Стандартные коды ошибок и `{ result: false, error: string }`
- **WebSocket (аудио)**: Graceful degradation при обрыве соединения, reconnection логика
- **Fallback**: При недоступности Realtime API переход на обычный STT + HTTP


## 4. Нефункциональные Требования

### 4.1. Производительность
- **Поисковые запросы**: < 200ms для семантического поиска (JS-уровень для до 1000 записей)
- **LLM интеграция**: < 3s для генерации обобщенного продукта
- **WebSocket уведомления**: < 50ms для broadcast сообщений
- **Поддержка векторного поиска**: до 1,000 продуктов с отличной производительностью на JS-уровне

### 4.2. Надежность
- **Fallback стратегия**: при недоступности LLM - простой текстовый поиск
- **Миграция данных**: с полным бэкапом перед изменениями
- **Graceful degradation**: работа без векторного поиска при проблемах с embeddings

### 4.3. Безопасность
- **Аутентификация**: все эндпоинты защищены `authMiddleware`
- **Единый каталог**: все пользователи имеют доступ к общему каталогу
- **Валидация входных данных**: строгие схемы Fastify для всех эндпоинтов
- **Валидация КБЖУ данных**: диапазоны допустимых значений
  - Калории: 0-1000 ккал на 100г
  - Белки, жиры, углеводы: 0-100 г на 100г
  - Клетчатка: 0-50 г на 100г
  - Название: минимум 1 символ, максимум 100 символов
  - Описание: минимум 1 символ, максимум 2000 символов
- **Race Conditions**: при одновременном редактировании одного продукта несколькими пользователями применяется стратегия "last write wins" (приемлемо для малого числа пользователей, версионирование не требуется)

### 4.4. Масштабируемость
- **Горизонтальное масштабирование**: возможность добавления read-replicas для поиска
- **Кэширование**: векторных представлений для часто используемых запросов
- **Batch обработка**: векторизации для множественных продуктов
- **JavaScript поиск**: оптимальная производительность для каталогов до 1,000 записей

## Приложение A: Типы и Примеры

### A.1. Структура данных

**Основной интерфейс продукта (CatalogueEntry):**
- Уникальный идентификатор записи каталога
- Обобщенное название (например, "Яблоко")
- Данные КБЖУ: калории, белки, жиры, углеводы, клетчатка (опционально)
- Описание для векторизации (опционально)

**Результат поиска (CatalogueSearchResult):**
- Объект записи каталога
- Коэффициент релевантности от 0 до 1

**Стандартный ответ API (SearchResponse):**
- Флаг успешности операции
- Данные (массив результатов поиска или null)
- Сообщение об ошибке (при неудаче)

**Запрос на создание продукта:**
- Текстовое описание продукта от пользователя

**Ответ от LLM сервиса:**
- Обобщенное название продукта
- Структура КБЖУ (калории, белки, жиры, углеводы, клетчатка)
- Коэффициент уверенности модели

**WebSocket события:**
- `CATALOGUE_ENTRY_SAVED` - универсальное событие при создании или обновлении продукта через `/save-product`
- Полезная нагрузка: полные данные записи каталога (id, name, kcals, protein, fat, carbs, fiber, description, legacyName, embedding)
- Назначение: синхронизация localStorage каталога на всех клиентах для корректной работы поиска и отображения обновленных данных
- Клиент проверяет наличие записи с данным ID в локальном каталоге для определения создания/обновления

### A.4. Основные операции с данными

#### Семантический поиск по общему каталогу
1. Загрузить все записи каталога с векторными представлениями
2. Выполнить векторный поиск на JavaScript-уровне с использованием косинусного расстояния
3. Отсортировать результаты по релевантности и ограничить количество

#### Legacy текстовый поиск (fallback)
1. Выполнить простой текстовый поиск по полю `legacyName`
2. Фильтровать записи каталога по вхождению поискового запроса
3. Отсортировать результаты по алфавиту

#### Создание записи каталога с проверкой существования
1. Проверить существование записи каталога с таким же названием
2. Если запись каталога не найдена - создать новую запись в `foodCatalogue` с полными КБЖУ данными
3. Продукт автоматически становится доступным всем пользователям

### 7.1. Персональные каталоги (идея на будущее)
**Концепция**: В будущем, при расширении пользовательской базы или по потребности, можно вернуться к системе персональных каталогов.

- Реализовать UI переключатель "Показывать только мои продукты"

**Преимущества персонализации**:

- Возможность создания тематических групп продуктов

**Миграционный путь**:
- Текущая архитектура легко расширяется для поддержки персонализации
- Все существующие продукты автоматически становятся видимыми всем пользователям

### 7.2. Расширенная категоризация
**Автоматические категории**: Использование LLM для автоматического определения категорий продуктов (фрукты, овощи, молочные продукты и т.д.)

**Фильтрация по категориям**: Возможность поиска и фильтрации продуктов по категориям

### 7.3. Социальные функции
**Рекомендации**: Система рекомендаций продуктов на основе предпочтений пользователей

**История популярности**: Отслеживание часто используемых продуктов для приоритизации в поиске

#### Управление векторными представлениями
**Сохранение embedding:**
- Сериализация Float32Array в Buffer для сохранения в BLOB поле
- При создании: генерация embedding через LLM API
- При обновлении: регенерация embedding только если изменились `name` или `description`
- Обновление записи каталога с новым векторным представлением

**Извлечение embedding:**
- Загрузка BLOB данных из базы
- Десериализация Buffer обратно в Float32Array для вычислений

**Оптимизация embedding при редактировании:**
- Сравнение старых и новых значений `name` и `description`
- Пропуск регенерации embedding если поля не изменились (экономия LLM API вызовов)
- Обновление только измененных полей КБЖУ без затрагивания embedding

#### Алгоритм косинусного расстояния
- Вычисление скалярного произведения векторов
- Расчет норм векторов
- Определение косинусного расстояния как меры похожести
