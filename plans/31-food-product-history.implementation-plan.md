# Food Product History — бэкенд (основной план)

## Описание

Новый read-only эндпоинт: по одному или нескольким продуктам каталога — постраничный, обратно-хронологический список всех фактов их употребления (дата, граммы, % от дневной нормы на тот момент). Питает новый блок статистики на фронте («История продукта»): пользователь ищет продукт, добавляет в список отслеживаемых, видит все дни/приёмы, когда он ел этот продукт (или несколько продуктов сразу).

Жёсткое требование пользователя: **без кэша**, без local-first — чистый запрос/ответ на каждое изменение состава отслеживаемых продуктов и на подгрузку следующей страницы.

## Текущая архитектура (релевантное)

- `foodDiary` — один ряд = один факт добавления продукта (`dateISO`, `foodCatalogueId`, `foodWeight`, `history`, `usersId`). **Нет UNIQUE(usersId, dateISO, foodCatalogueId)** — создание записи всегда `INSERT`, повторное добавление того же продукта в тот же день = отдельный ряд. Значит, гранулярность «когда» — на уровне ряда (события), а не дня; `id` внутри пользователя монотонно возрастает вместе с моментом создания записи (кроме редкого кейса ручного бэкдейтинга, для сортировки это не критично — обрабатывается композитным ключом сортировки).
- Индекс сейчас: `idxFoodDiaryUserDate (usersId, dateISO)`. Для нового запроса (фильтр по `usersId` + `foodCatalogueId` + сортировка по `dateISO`) нужен новый композитный индекс.
- Дневная норма и калорийность продукта — не статичные значения, а персональные, помесячные (GA2, план 04): `foodPersonalNormHistory` / `foodPersonalKcalHistory`, применяются через decay-averaging + капы. Готовый строительный блок — `Service.buildPersonalKcalResolver(ctx, userID)`, уже используемый в `buildStatsSummary` для точно такой же задачи (посчитать % дня от нормы). Новый эндпоинт переиспользует его один-в-один, без нового математического кода.
- Пагинации в проекте нет нигде — ни в food, ни в money. Это первый эндпоинт с постраничной выдачей, паттерна для копирования нет.
- Два конвенции ответа сосуществуют; новые эндпоинты (поиск, save-product) сходятся к обёртке `{result, data}` через `internal/httpx/legacy` — новый эндпоинт следует этой же конвенции.
- Маршруты — chi, группа `/api/food` с `auth.Middleware`, хендлер получает `userID` из `auth.UserClaimsFromContext`.

## Архитектурное решение

### Контракт эндпоинта

- Новый `GET` в группе `/api/food`, на чтение — рядом с остальными read-хендлерами (`http.go`).
- Вход: список id продуктов (один или несколько), размер страницы, курсор предыдущей страницы (опционален для первой страницы).
- Курсор — не opaque-токен, а два простых параметра: дата и id последнего ряда предыдущей страницы. Это соответствует духу проекта (никаких кодирований ради кодирования) и однозначно продолжает сортировку `(dateISO DESC, id DESC)`.
- Размер страницы — с дефолтом и жёстким верхним потолком на стороне сервера (клиент не может запросить произвольно много), по аналогии с уже существующим потолком в 30 результатов поиска.
- Выход: плоский список рядов (дата, id продукта, граммы, % от нормы на тот момент), плюс признак/курсор «есть ли следующая страница». Имя продукта в ответ не кладём — фронт уже знает имена отслеживаемых продуктов из момента их добавления через поиск, лишнее поле — лишний JOIN и лишний трафик. Ккал в ответ тоже не кладём — фронт калории нигде не отображает, это чисто промежуточная величина для расчёта %.
- Неизвестные/чужие id продуктов не считаются ошибкой — просто не дают рядов (тот же принцип терпимости, что и у прочих read-эндпоинтов).
- Валидационная ошибка — только на действительно некорректный ввод (пустой список id, если фронт всё же его пришлёт, хотя по флоу фронта пустой список означает «не делать запрос вообще»).

### Расчёт процента от нормы

Один-в-один переиспользуется существующая формула из `buildStatsSummary`: для каждого ряда — `resolver.AppliedKcal(catalogueID, yearMonth продукта) * граммы / 100`, знаменатель — `resolver.AppliedNorm(тот же yearMonth)`. `yearMonth` берётся из `dateISO` самого ряда (историческая точность — норма и калорийность применяются такими, какими были в месяц события, а не текущими). Резолвер строится один раз на запрос (`buildPersonalKcalResolver`), дальше — чистые вычисления в памяти, без дополнительных обращений к БД на ряд.

### Пагинация

Keyset-пагинация по `(dateISO DESC, id DESC)` — устойчива к вставке новых записей между подгрузками страниц (в отличие от offset), дёшева при наличии индекса. Фильтр — `usersId = ?` (обязательно, из сессии) `AND foodCatalogueId IN (...)` `AND (dateISO, id) < (курсор)`.

### Индекс

Новая миграция `000011`, композитный индекс `(usersId, foodCatalogueId, dateISO)` на `foodDiary` — без него запрос по нескольким продуктам с сортировкой по дате будет full-scan по всей истории пользователя.

### Отсутствие кэша — явно

Ни `CatalogueCache`, ни `StatsCache` не участвуют. Хендлер → сервис → репозиторий → живой SQL-запрос при каждом вызове. Это осознанное расхождение с остальным food-доменом, соответствует явному требованию пользователя (список отслеживаемых продуктов меняется часто, кэшировать нечего — результат один раз использовал и выбросил).

## Чеклист

- ✅ Миграция `000011_food_diary_product_history_index.sql` — композитный индекс `(usersId, foodCatalogueId, dateISO)` на `foodDiary`
- ✅ Репозиторный метод: выборка рядов `foodDiary` по `usersId` + набору `foodCatalogueId` + keyset-курсору, с `LIMIT n+1` (для определения «есть ли следующая страница» без отдельного `COUNT`)
- ✅ Сервисный метод: строит резолвер через `buildPersonalKcalResolver`, для каждого ряда считает ккал как промежуточную величину и % от нормы (ккал в ответ API не попадает — фронт его не отображает), собирает страницу + курсор следующей страницы
- ✅ Хендлер: парсинг query-параметров (список id, лимит с клампом, курсор), вызов сервиса, ответ в конвенции `{result, data}` (локальный `writeJSON`, как у соседних read-хендлеров `http.go`)
- ✅ Регистрация маршрута в `RegisterRoutes` (`http.go`), под `auth.Middleware`
- ✅ Валидация: пустой список id → 400; лимит вне диапазона клампится сервисом, не ошибка; некорректный `limit`/`cursorId`/`catalogueIds` → 400
- ✅ Тесты: репозиторный тест на keyset-пагинацию (граница страницы, несколько продуктов вперемешку по датам, бэкдейтнутая запись, два события в один день); сервисный тест на корректность % + курсор через две страницы; `httptest`-тест хендлера (форма ответа, отсутствие поля `kcal` в ответе, курсор по HTTP, 400-кейсы)
- ✅ Прогон `go build ./... && go vet ./... && go test ./...` — зелёно
